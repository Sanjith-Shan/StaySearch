# Bug log

Each bug, how it showed up, the tool that found it, and the fix. Newest last.

| # | Milestone | Bug | Found by | Fix |
|---|---|---|---|---|
| 1 | M0 | `staysearch/data/` (the download package) shadowed `staysearch/data.py`, so `from staysearch.data import CITY_LIST` failed | Python `ImportError` on the first baseline run | Renamed the package to `staysearch/ingest/` |
| 2 | M0 | The first label builder kept every review as a Python tuple (10.9M) and every kept stay as a dict; on a machine already under memory pressure this was several GB | Sizing query in DuckDB before the first full run (5.4M reviews since 2023-09) | Rewrote it vectorized in NumPy; guest history became an index range into one (reviewer, date)-sorted review array instead of a per-row list. Full build: 45 s |
| 3 | M0 | Quarterly snapshots are not uniform: Seattle 2025-12-28 and 2026-03-29 have no `price` values at all, and S3 (March 2026) holds about 30% fewer listings than its neighbours across all ten cities | DuckDB `count(price)` per snapshot during ingest checks | Not a code bug, a data fact. Price is carried forward from the latest earlier snapshot with a quote (point in time), the missing share is reported per city in `results/m0_data.jsonl`, and the README states both |
| 4 | M1 | Expected rank under ties was `greater + (ties + 1) / 2`, half a place too good (the mean of positions `greater+1 .. greater+ties+1` is `greater + 1 + ties/2`). Recall and NDCG were already correct; only the reported mean rank was off | pytest `test_ties_are_expected_values` | Corrected the formula before any rank was reported |
| 5 | M3 | The Kotest property test for the hard invariant drew a NaN box size: `Arb.double(min, max)` includes non-finite edge cases by default, and the service (correctly) rejected the NaN box with `bbox min must be <= max` | Kotest property test, shrunk to the NaN case on attempt 66 | Generator restricted to finite values (`includeNaNs = false`); the service's rejection of a non-finite box stays as the 400 path |
| 6 | M4 | Ranker training lists forced the reviewed stay in when retrieval missed it, by replacing the K-th candidate. The forced positive was then always the candidate with the largest retrieval distance, so the rankers learned "farther in embedding space means reviewed" and scored below the retrieval order they were re-ranking (debug run: NDCG@10 0.07 vs 0.107) | Debug run of `staysearch.ranking`: every learned ranker below the `retrieval_order` baseline, which should be impossible for a ranker that has retrieval distance as a feature | Training lists now keep only queries whose positive retrieval found on its own, which is also the only case the ranker can affect at serving time |
| 7 | M3 | On Windows, Gradle's generated `staysearch-service.bat` failed with "The input line is too long": it spells out every jar on the classpath, and with Lucene, ONNX Runtime, Ktor and JMH that passes cmd's 8,191-character limit | minipc job log on the first service-experiment run | The mini PC script calls `java -cp "lib\*" staysearch.cli.MainKt` directly with the same JVM options |
| 8 | M3 | In the mini PC experiment script, `--rates 25,50,100,200` reached the JVM as four separate arguments: PowerShell parses an unquoted comma list as an array and splats each element, so the service's argument parser threw "unexpected argument '50'" | The service's strict argument parser (it rejects unknown positionals instead of ignoring them), seen in the minipc job log | Comma lists quoted in the script |
| 9 | M3 | The open-loop load generator waited for each arrival's due time with `LockSupport.parkNanos(wait)`. On Windows that oversleeps by up to one timer tick, so latency measured from the intended send time read about 10 ms at p50 while the service's own stages summed to 2.2 ms, even at 25 queries/s where nothing queues | The first exp9 run on the mini PC: an 8 ms gap between "from intended" and "service total" that did not move with load, which ruled out queueing | Park until shortly before the due time, then spin; the generator's own dispatch lag is now recorded and reported next to every latency figure. A 2 ms spin window still left 6 ms p50 lag on Windows, whose default timer tick is about 15.6 ms, so the window is 16 ms there (the generator then spins on one of the four cores, stated with the results). The exp9 and exp4 runs were redone |
